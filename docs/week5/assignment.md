# 5주차 과제 / 반복 보고를 위한 마트 제안서

[강의](lecture.md) / [실습](lab.md) / [분석 보고서 양식](../templates/analysis-report.md)

예상 시간은 90–120분입니다. 개인별 SQL과 검증 기록을 작성하고 팀에서는 서로 결과를 리뷰하는 운영안을 제안합니다. 최종 제출 단위는 [프로젝트 안내](../project.md)의 공지를 따릅니다.

## 질문 1. 월간 소비 리포트에 어떤 마트가 필요한가? / 35분

> 담당자가 월별 순거래액, 업종별 순위, 온라인과 오프라인 사기율을 한 화면에서 보고 싶어 합니다. 오늘 마트로 어떤 질문에 답할 수 있고 어떤 질문에는 답할 수 없을까요?

다음 내용을 한 페이지 안에 작성합니다.

- 답할 수 있는 질문 세 개와 답할 수 없는 질문 두 개.
- 결과 한 줄에 무엇을 담는지 한 문장으로 설명하고, 각 열이 숫자인지 글자인지와 계산 방법을 적기.
- 기간, 승인 교육용 조건, 환불, 금액 결측, 사기 라벨 결측 정의.
- 원본 데이터가 바뀌면 마트를 어떻게 다시 만들고, 언제 만든 데이터인지 어떻게 표시할지.
- 날짜, 업종 필터를 고려한 저장 구조 선택과 그 근거.

자신의 `mart_monthly_mcc` 생성 SQL과 검증 SQL을 제출합니다. 날짜별 변화나 중복을 뺀 고객 수는 현재 마트만으로 계산할 수 없습니다. 이런 숫자가 필요하다면 어떤 정보를 더 가져와야 하고 새 표의 한 줄에는 무엇을 담아야 할지 제안하세요.

<details markdown="1">
<summary>힌트 / 답할 수 없는 질문 찾기</summary>

“10월 15일에 거래가 급증했는가?”에는 월 집계만으로 답할 수 없습니다. “전체 활성 고객 수는 몇 명인가?”도 고객 식별자가 없는 마트로 계산할 수 없습니다. `COUNT(*)`는 집계 행 수이고 `SUM(txn_count)`는 거래 건수입니다.

</details>

## 질문 2. 반복 조회 비용이 줄었다고 말할 근거는 무엇인가? / 30분

> 같은 리포트를 매주 여러 번 연다면 원본, 뷰, 마트 가운데 무엇을 선택하겠습니까?

[실습 C](lab.md)의 세 쿼리로 결과와 바이트를 기록합니다. 실제 환경에서 실행할 수 없었던 항목은 “미측정”으로 표시하고, 예상값을 실측값처럼 쓰지 않습니다.

| 항목 | 반드시 기록할 내용 |
| --- | --- |
| 비교 질문 | 기간과 출력 지표가 정확히 같은지 |
| 결과가 같은지 확인 | 월별 행, 금액, 건수 비교 결과 |
| 비용 관찰 | 실행 전 예상 바이트, 실행 후 바이트, 캐시 여부 |
| 별도 비용 | 마트 생성, 갱신, 저장 비용을 포함했는지 |
| 결론 | 이번 측정 범위에서 선택한 방식과 한계 |

결론은 “마트는 언제나 저렴하다” 대신 “이번 질문, 데이터, 반복 횟수 조건에서는 …를 선택하겠다”로 씁니다. 측정값을 USD로 바꾸는 것은 필수 과제가 아닙니다.

<details markdown="1">
<summary>힌트 / 결과가 같지 않을 때의 점검 순서</summary>

기간 → 승인 조건 → 금액 NULL → 음수 환불 → 거래 건수 정의 순서로 확인합니다. `SUM`을 다시 `SUM`하는 마트 쿼리가 `AVG`나 `COUNT(*)`로 바뀌지 않았는지도 확인합니다. 먼저 세 방식의 계산 결과를 같게 맞춘 뒤 어느 방식이 비용을 줄였는지 적습니다.

</details>

## 질문 3. AI가 만든 개선안은 정말 개선인가? / 25분

> AI가 “빠르고 저렴한 SQL”을 제안했습니다. 팀에 채택을 권할 수 있을까요?

자신의 SQL 한 개를 AI에 주고, 중간 결과의 이름과 설명 주석을 이해하기 쉽게 바꿔 달라고 요청합니다. 계산 결과는 그대로여야 합니다. 생성된 변경 사항 중 하나를 선택해 검증합니다. 바이트가 줄지 않아도 가독성이나 정의 통일에 도움이 되었다면 그 근거를 쓰면 됩니다.

제출 기록은 다음 순서로 작성합니다.

1. AI에 제공한 스키마와 분석 조건.
2. AI가 생성한 코드 범위와 핵심 변경.
3. 직접 확인한 한 행의 기준, 행 수, 합계, NULL, 경계 날짜.
4. 비용 절감 주장과 실제 관찰값의 일치 여부.
5. 채택/부분 채택/거절 판단과 수정한 SQL.

교육용 가상 예시로 반례를 만들어도 됩니다. 이 경우 원본 측정 결과와 별도 구역에 “교육용 가상 데이터”라고 표시합니다. 인증 정보와 개인 정보는 AI 프롬프트, 캡처, 저장소에 포함하지 않습니다.

## 제출 파일

```text
week5/

  03_validate_mart.sql
```

`metric-spec.md`에는 자신의 역할과 팀 리뷰를 받은 항목을 한 줄로 남깁니다. 스크립트에는 자신의 프로젝트 ID가 들어 있어도 토큰, 키는 들어 있으면 안 됩니다. 공개 포트폴리오용으로는 원본 프로젝트 접근이 필요한 부분을 설명하고 다른 사람이 자신의 프로젝트 ID를 넣어 쓸 수 있도록 `YOUR_PROJECT` 같은 표시를 넣은 예시도 준비합니다.

## 평가 기준과 완료 체크

아래 비중은 강사가 조정할 수 있는 학습 피드백 제안입니다. 학회 공식 평가 배점으로 확정된 값은 아니며 최종 공지를 따릅니다.

| 기준 | 비중 | 확인할 증거 |
| --- | ---: | --- |
| 마트 설계 | 30% | 질문, 한 행의 기준, 열, 집계 규칙의 일치 |
| SQL 정확성 | 30% | 유효 범위와 더해서 합계를 구할 수 있는 지표, 합계, 중복 검사 |
| 비용 판단 | 20% | 동일 결과 비교와 실제 측정, 캐시 조건 |
| AI 검증 설명 | 20% | 생성 부분, 검증 방법, 채택 근거 |

- [ ] 사기율은 `SUM(fraud_count) / SUM(fraud_labeled_count)`이다.
- [ ] 객단가는 `SUM(amount_usd) / SUM(txn_count)`이다.
- [ ] 현재 마트가 답할 수 없는 질문을 명시했다.
- [ ] 생성 SQL을 다시 실행할 위치와 범위를 설명했다.
- [ ] 6주차 대시보드에 넘길 열과 데이터 갱신 시점을 준비했다.
- [ ] [Streamlit 연결 안내](../reference/dashboard-connection.md)를 따라 기본 앱을 미리 열어 보았다. 서비스 계정이 막히면 Colab 본인 로그인으로 마트를 조회할 수 있는지 확인했다.
