# 6주 핵심 정리

좋은 분석 결과는 쿼리 하나로 끝나지 않습니다. 질문의 정의, 데이터 범위, 숫자의 검증, 전달 방식이 맞물려야 합니다.

| 회차 | 남겨야 할 습관 | 확인 질문 |
| --- | --- | --- |
| 1 | 스키마와 처리 바이트 먼저 보기 | 이 컬럼은 실제로 있고 어떤 타입인가? |
| 2 | 지표의 분자·분모 합의 | 금액·건수·고객 수가 같은 범위인가? |
| 3 | 키와 조인 보존 검사 | 고객·카드를 붙여도 거래액이 유지되는가? |
| 4 | 기간과 집단으로 분해 | 변화가 어디서 일어났고 어디까지 해석할 수 있나? |
| 5 | 그레인과 재사용 기준 만들기 | 한 행의 의미가 무엇이며 반복 조회를 줄이는가? |
| 6 | 앱과 SQL의 숫자 대조 | 필터를 바꿔도 같은 정의가 유지되는가? |

## 발표 전에 다시 읽을 문장

- 실행됐다고 올바른 SQL은 아닙니다.
- NULL은 0과 다르고, 결측 사기 라벨은 정상 라벨과 다릅니다.
- 복합 키에서 조건 하나가 빠지면 행과 금액이 늘어날 수 있습니다.
- `LAG`는 이전 행을 반환하며, 자동으로 이전 달을 찾아주지 않습니다.
- 논리 뷰는 재사용을 돕지만 비용을 자동으로 낮추지 않습니다.
- 평균과 비율은 분자·분모 합으로 다시 계산해야 할 수 있습니다.
- AI가 붙인 원인 설명은 데이터 표에서 바로 확인되는 사실과 다릅니다.
- 공개 Streamlit 앱은 집계 마트를 읽고, 인증값은 Secrets에 보관합니다.

## 과정 후 혼자 확장할 때

새 데이터가 생기면 바로 앱부터 만들지 말고 1주차의 스키마·품질 확인부터 시작하세요. 데이터가 작아도 기간·그레인·정의·검증의 순서는 같습니다. 잘 만든 SQL과 검증 기록은 새로운 도구로 옮겨도 재사용할 수 있습니다.
