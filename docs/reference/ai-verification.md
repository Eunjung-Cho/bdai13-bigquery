# AI SQL 검증 체크리스트

AI는 스키마와 질문을 바탕으로 그럴듯한 SQL을 생성합니다. 데이터베이스에 실제로 있는 컬럼인지, 그 결과가 질문에 맞는지는 별도로 확인해야 합니다. 검증은 코드 실행 전·실행 후·해석 후 세 번 합니다.

## 실행 전

| 검사 | 질문 | 확인 근거 |
| --- | --- | --- |
| 스키마 | 컬럼명·타입이 실제로 존재하는가? | Schema·INFORMATION_SCHEMA |
| 목적 | 한 행이 무엇을 뜻하는가? | 지표 정의서 |
| 범위 | 날짜·환불·오류 거래 조건이 같은가? | WHERE·CTE |
| 조인 | 양쪽 키와 관계가 맞는가? | 키 중복 검사 |
| 비용 | 필요한 컬럼과 범위만 읽는가? | 예상 바이트·최대 청구 바이트 |

## 실행 후

결과가 너무 그럴듯할수록 기준을 하나씩 대조합니다.

- 전체 합과 세그먼트 합이 일치하는가? 세그먼트가 겹치면 합산 가능하지 않을 수 있습니다.
- LEFT JOIN 전후 거래 행 수와 금액 합이 같은가? 다르면 오른쪽 키 중복부터 확인합니다.
- INNER JOIN으로 없어진 거래는 얼마나 되며 제외할 이유가 있는가?
- SAFE_CAST 실패 건수와 원본 문자열을 확인했는가?
- 비율의 분모가 0 또는 NULL일 때 계산 불가가 표시되는가?
- 사기 라벨의 TRUE·FALSE·NULL이 전체 대상 행을 설명하는가?
- 순위에 동점이 있을 때 결과가 다시 실행해도 안정적인가?
- 전월비의 이전 행이 실제 이전 달인가? 빠진 월이 있지 않은가?

## 해석 후

AI 요약과 결과표를 나란히 놓고 숫자, 증가·감소 방향, 기준 기간을 대조합니다. “비중이 커졌다”는 말은 절대 거래액 증가와 다릅니다. “전체가 줄었다”는 말은 일부 업종이 늘어난 것과 동시에 성립할 수 있습니다.

| AI 문장 | 확인할 질문 |
| --- | --- |
| A 채널이 더 위험하다 | 관찰된 라벨 비율인가, 위험의 인과 효과를 입증했는가? |
| 매출이 20% 증가했다 | 분모·분자·단위와 비교 월을 실제 표에서 찾을 수 있는가? |
| 고객이 이탈했다 | 이탈의 관측 가능 정의가 있는가, 단순 휴면인가? |
| 뷰로 바꿔 비용이 절약된다 | 같은 결과에서 처리 바이트를 실제 비교했는가? |

위 문장들은 오류를 찾기 위한 예시이며 실데이터 분석 결과가 아닙니다.

## 매주 사용하는 검증 루틴

```mermaid
flowchart LR
    D[정의와 스키마 제공] --> A[AI SQL 초안]
    A --> R[직접 읽기와 예상 결과]
    R --> Q[실행과 검사 SQL]
    Q --> F[수정 이유 기록]
    F --> S[표와 해석 교차 확인]
```

## 재사용 프롬프트

```text
BigQuery GoogleSQL로 다음 비즈니스 질문에 답하는 쿼리를 작성해 줘.
질문: [질문]
스키마: [실제 컬럼과 타입]
원천: finda-13-2026.tabformer.[테이블]
결과 한 행: [그레인]
기간/환불/오류/NULL 처리: [정의]

1. 먼저 필요한 가정을 설명해 줘.
2. 없는 컬럼이나 결과 숫자를 만들지 마.
3. SQL과 별도로 행 수·합계·NULL·조인 검증 쿼리를 제시해 줘.
4. SQL을 단계별로 쉬운 한국어로 설명해 줘.
5. 실행하지 않았다면 검증 완료라고 말하지 마.
```

## Streamlit 코드를 검토할 때

AI에게 한 번에 전체 앱을 다시 쓰게 하지 말고 “기간 필터만 추가”처럼 변경을 작게 요청합니다. 기존 지표 계산, 쿼리 상한, Secrets 사용은 유지하도록 명시합니다. 수정 전후 동일 조건에서 SQL과 앱 숫자를 대조하고, 데이터 없음·0분모·잘못된 연결 설정도 확인합니다. 공개 앱에 임의 SQL 입력창은 넣지 않습니다.
